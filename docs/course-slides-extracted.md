快速诊断：你认为“AI完成任务”的证据是什么
场景：Agent 报告“功能已经完成，所有问题均已修复。”——下列哪些可以作为证据？请排序
A
　Agent 的文字说明
B
　页面演示成功一次
C
　Git Diff
D
　自动测试通过
E
　隐藏测试通过
F
　日志和指标正常
G
　另一组在干净环境中复现
H
　教师现场提出变更后仍能正确修改
教师引导：每张卡“能证明什么、不能证明什么”
A 自述只提供线索，不能独立证明完成；B 一次成功只覆盖一条路径；C Diff 说明改了什么，不证明改得正确；
D 公开测试可能不完整或被绕过；E 隐藏测试降低针对性刷分；F 日志指标证明运行状态；
G 干净环境复现证明可重复；H 面对新变化仍能修改，检验是否真正理解系统。
不是选一个“最正确答案”，而是给证据排序：结论的可信度取决于证据组合。
来源：课程设计；W4 ｜ 流程：3分钟个人排序 → 3分钟小组讨论 → 2分钟全班汇总（教师暂不给出固定答案）

上下文管理的三个常见误区
 纠正 
上学期把上下文当作“聊天窗口”，本学期要把它当作需要设计和审计的工程资源
误区 1
　
“上下文越多越好”
错误做法：把整个仓库塞进 Prompt。
后果：成本上升、注意力稀释、敏感信息泄露风险增加。
正确原则：
最小必要上下文（Minimum Necessary Context）——只给完成任务所需的最小集合。
误区 2
　
“贴文件路径就等于给了上下文”
错误做法：在 Prompt 里写“参考 src/auth/ 下的代码”。
后果：Agent 可能读错版本、遗漏依赖关系、遇到权限边界时静默失败。
正确原则：
上下文 = 显式选取的文件片段 + 结构化摘要 + 访问权限说明。
误区 3
　
“上下文只在 Prompt 里”
错误做法：认为只要把 Prompt 写好就万事大吉。
后果：忽略了工具返回、系统消息、历史轨迹、环境状态都是上下文的组成部分。
正确原则：
上下文是
整个运行环境的信息总和
，需要在架构层面管理。

Given–When–Then：写可执行规格的最小语法
三句式结构让每条规格自带前置条件、触发动作、可断言结果——也是给 AI 下指令的高质量格式
Given 给定
系统处于什么状态、存在哪些前置数据。
例：用户已登录，论文状态为“待审核”
When 当
发生什么动作或事件。
例：审核员点击“通过”
Then 则
可观察、可断言的结果。
例：状态变为“已录用”，作者收到通知
一条合格规格的四个自检问题
Q1 状态可构造吗？
Given 里的前置条件能用测试数据搭出来。
Q2 动作可触发吗？
When 是明确的单一动作，不是一串过程。
Q3 结果可断言吗？
Then 的每条结果都能写成 assert。
Q4 与实现解耦吗？
规格描述行为，不规定用哪个类哪个函数。
练习：为“投稿截止后禁止再提交”写一条 Given–When–Then，并回答四个自检问题。

单元 01　|　15

为什么 Non-goal 在 AI 时代更重要
Coding Agent 常见失效：过度实现。
看到“校外专家”就顺手增加注册、找回密码、个人中心、通知系统与一整套用户管理。
这些功能看起来“完整”，却偏离本次任务，扩大测试与维护面。
Non-goal 的两个作用
① 
切断解空间
：即使发现问题，也不在当前任务中扩展；
② 
支持答辩
：能说明“未实现”是明确决策的范围限制，而不是遗漏。
没有 Non-goal 的 Specification，等于把范围决策权默认交给了执行者。

事实、假设、决策、未决问题：必须分开记录
防止 AI 将推测写成事实——“推测固化”是 AI 协作中的常见失效模式

已被证据确认
例：旧接口返回 paperId 和 status
Assumption 假设
暂时接受但尚未验证
例：校外专家每次只评一篇论文
Decision 决策
已由负责人选择
例：使用短期邀请而非长期账号

文档篇幅不是加分项；短而可执行的规格，优于冗长但模糊的文档。
02
用 AI 不扣分
使用 AI 生成结构化文本本身不扣分；无法解释、无法验证或与仓库不一致才扣分。
03
不确定性可保留
高分组不必消除所有不确定性，但必须能正确识别高风险不确定性，并建立处理机制。
04
不看文件名
Harness 评分不以某个文件名为标准，而看它是否真正改善 Agent 和团队的执行条件。
评分对象是学生面对模糊与风险时的工程行为，而不是他们提交的 Markdown 有多漂亮。
来源：课程评分校准说明（6.2）。

同行审查：三轮，各查一件事
每一轮只回答一类问题，避免审查变成泛泛的“写得不错”
第一轮 · 边界审查
· 被审查组到底解决什么问题？
· 哪些内容明确不做？
· 哪些关键假设尚未验证？
· 哪个不变量一旦破坏，项目即失败？
第二轮 · 可验证性审查
· 随机抽三条 MUST 反向追踪：Requirement → Scenario → 可观察结果 → 验证方式 → 负责 Task。
· 链条中间任意一环缺失，即形成一项审查发现。
第三轮 · Harness 可用性审查
· 在干净环境中：按 Repository Map 找到关键模块；执行至少两条 Validation Command；
· 判断 Allow / Deny / Ask 是否存在冲突；找出一条已过时或无法机械检查的规则；模拟一次 Stop / Rollback。
来源：课程同行审查组织方式（6.3）。Peer Review 不直接决定对方成绩；教师最终复核 Blocking Finding。
